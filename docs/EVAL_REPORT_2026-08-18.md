# 평가 리포트 — 2026-08-18 (1차 목표: 단일 화자)

방법론은 `docs/EVAL.md` 기준. 데이터셋은 `data/json`/`data/wav`의 게임/여행/음식,요리/일상,소통/패션,뷰티
5개 카테고리 150클립 중 단일 화자(`li_total_speaker_num == "1"`) 120클립만 사용 —
2차 목표(다중 화자)는 아직 범위 밖 (`CLAUDE.md` 참고).

## 실행 환경 — 주의

이 평가는 **CPU**(faster-whisper `medium` int8, llama-server CPU 빌드로 Qwen2.5-7B-Instruct
Q4_K_M)로 돌렸다. 실제 서비스는 `config.py` 기준 CUDA + int8_float16. STT/번역의 **디코딩
파라미터(beam_size=5, 프롬프트, grammar)는 동일**하지만, VAD 기반 실시간 세그멘테이션·
provisional 패스·문맥 연속성(`context`)·glossary hotwords는 이번 평가에 포함되지 않았다 —
사람이 이미 잘라둔 클립을 STT에 한 번에 통째로 넣고 final 패스만 측정했다. 정밀도(GPU
int8_float16 vs CPU int8) 차이가 아래 수치를 크게 바꿀 것으로는 보이지 않는다.

재현: `python scripts/build_eval_set.py` → `python scripts/run_eval.py` → 사람/LLM 채점.

## 3. 원인 분리 — STT 전파 vs 번역 자체 (§3.4)

S1 61건을 세그먼트 단위로 원인 분리:

| 원인 | 건수 | 비율 |
|---|---|---|
| STT 전파 | 42 | 69% |
| 번역 자체 | 19 | 31% |

코퍼스 레벨 교차검증(`scripts/eval_stt_propagation.py`) — `ja_ref`(정답 전사)를 STT 없이
바로 번역기에 넣었을 때 chrF++가 얼마나 오르는지로 같은 결론을 다른 방식으로 재확인:

| 그룹 | n | chrF++ (STT hyp 번역) | chrF++ (정답 전사 직접 번역) | gap |
|---|---|---|---|---|
| normal | 94 | 17.07 | 25.00 | +7.94 |
| hard | 26 | 17.87 | 22.70 | +4.84 |
| 전체 | 120 | 17.33 | **24.25** | **+6.92** |

STT 오류를 완전히 없애도(정답 전사를 그대로 넣어도) chrF++가 24.25에 그침 — "잘 되는 MT"
기준(40~60+)에 한참 못 미친다. 즉 STT가 약 6.9점만큼 번역 품질을 깎아먹는 건 맞지만(§3.4
S1 카운트 기준 "STT 전파 69%"와 같은 방향), **입력이 완벽해도 번역 엔진 자체 품질이
낮다는 게 코퍼스 레벨에서도 확인됨** — S1 카운트 기준의 31%보다 번역 엔진 자체 비중이 더
클 수 있다는 뜻. 패턴 C(번역 자체 오역)를 STT 개선과 병행해서 다뤄야 하는 근거.

## 4. 반복 오류 패턴 3가지

### 패턴 A — STT 무출력 (23건, S1의 38%, 최대 단일 원인)
`no_speech_prob >= 0.6`(`config.py`) 필터가 짧고 조용한 클립을 통째로 드롭해 아무 텍스트도
안 나옴. **23건 중 22건이 단일 소스 영상(`7112`, 게임 카테고리)에 몰려 있음** — 이 영상의
클립들은 RMS가 다른 클립 대비 약 1/30(정상 300~4000대 vs 이 영상 33~44)로, 원본 녹음
자체가 매우 조용함. Whisper가 이런 저음량 구간을 "無음성"으로 오판하고 환각(예: "ご視聴
ありがとうございました")하거나 완전히 드롭한다 — `stt/faster_whisper_engine.py` 상단
주석에 이미 기록된 바로 그 실패 모드.

### 패턴 B — 고유명사 동음이의 오인식이 번역까지 전파 (S1 42건 중 다수)
- マッターホルン(마터호른) → "정말 내려갈 거예요?"
- 千恵子先生(치에코 선생님) → "체코 선생님" (국가명으로 둔갑)
- 白馬岳(하쿠바다케) → だけ

`backend/glossary.py`/`glossary.json` 인프라(STT hotwords + 번역 glossary_hint)가 정확히 이
문제를 위해 만들어져 있으나, **`glossary.json`이 현재 비어 있음**(커밋 `b81a8fe`에서 다른
버그를 격리하려고 비운 채로 방치됨).

### 패턴 C — STT는 맞았는데 번역기가 스스로 오역 (S1 19건)
- 寿司(초밥) → "오징어" (3회 이상 반복 재현)
- いただきます(잘 먹겠습니다) → "드리겠습니다" (의미가 정반대로 뒤집힘)
- プリン(푸딩) → "림프"

STT 오류와 무관하게 번역 엔진(Qwen2.5-7B-Instruct Q4_K_M) 자체가 특정 일본어 관용구/명사를
반복적으로 틀림. 같은 단어가 여러 세그먼트에서 반복적으로 같은 방식으로 틀리는 것으로 보아
무작위 노이즈가 아니라 이 모델의 체계적인 약점으로 보인다.

### 패턴 D — 머뭇거림/중간 끊김에서 문장이 조기 종결됨 (실사용 관찰, 자동 지표엔 미반영)
이번 평가 데이터셋은 사람이 이미 문장 경계를 잘라둔 클립이라 이 문제를 잡아내지 못한다.
실제 유튜브 라이브로 확인한 바로는: 화자가 "우... 음... 아~~"처럼 머뭇거리거나 "아, 이거
하기로 했지. 자아아암시.... 만요!"처럼 말 중간에 끊기면, `audio_session.py`의
`_process_frame`이 `silence_ms >= VAD_SILENCE_MS`(600ms) 하나만으로 즉시
`_finalize_utterance()`를 호출한다. `CLAUDE.md`의 설계는 "침묵 감지(1차 트리거) +
구두점/문맥 분석(보정 단계)"을 **분리된 두 단계**로 요구하는데, 현재 코드에는 침묵 트리거만
구현돼 있고 보정 단계가 없다. 그 결과 문장이 끝나지 않았는데 잘린 조각이 그대로 번역기에
들어가 엉성한 번역이 나온다.

## 5. 개선 계획

우선순위는 S1 기여도 순(패턴 A > B > C).

### A. STT 무출력 (최우선 — S1의 38%)
1. **오디오 게인 정규화 추가** — `audio_session.py`에서 STT에 넘기기 전 발화 버퍼를 RMS 또는
   피크 기준으로 정규화. 실시간 스트림 어디서든 저음량 소스가 나오면 재발할 문제라 데이터셋
   특이값이 아니라 파이프라인 차원에서 고쳐야 함.
2. **VAD와 no_speech_prob의 판단 불일치를 신뢰 신호로 활용** — silero-VAD(`vad.py`)가 이미
   "이건 발화다"라고 판단해서 버퍼를 만들었는데 Whisper의 `no_speech_prob`가 이를 뒤집는
   상황이므로, 이 경우 무조건 드롭하지 말고 게인 정규화 후 재시도하거나 임계값을 완화하는
   재시도 로직 고려.
3. 위 변경 후 `7112` 클립들만 별도로 재평가해 개선 폭 확인.

### B. 글로서리 채우기 (고유명사 오인식 전파)
1. `glossary.json`을 실제 사용 맥락(스트리머 이름, 게임 용어, 지명 등)으로 다시 채운다 —
   이미 있는 hotwords/glossary_hint 배선을 그냥 쓰면 됨, 코드 변경 불필요.
2. 이번 평가에서 나온 고유명사 오인식 사례(マッターホルン, 千恵子先生, 白馬岳 등)를 시드로
   우선 등록.
3. glossary 재도입 후 동일 데이터셋으로 재평가해 `b81a8fe`에서 격리하려던 원래 버그가
   재발하는지도 함께 확인(글로서리를 비웠던 이유 자체를 검증).

### C. 번역 엔진 자체 오역
1. `寿司`→"오징어" 같은 재현 가능한 오역 사례를 모아 최소 재현 세트로 만들고, grammar
   제약(`_KOREAN_ONLY_GRAMMAR`)/`repeat_penalty` 없이 같은 입력을 넣었을 때도 재현되는지
   확인 — 디코딩 제약이 원인인지 모델 자체 한계인지 분리.
2. `CLAUDE.md`가 이미 열어둔 대로, 다른 번역 모델(더 큰 Qwen2.5 사이즈, 또는 다른 MT 특화
   모델)을 같은 평가셋으로 벤치마크해 비교.
3. (2)로 근본 해결이 안 되면 반복 재현되는 특정 오역 단어들만 우선 `_FINAL_SYSTEM_PROMPT`에
   짧은 "자주 틀리는 표현" 힌트로 패치 — 임시방편이므로 (2) 결과가 나오기 전까지만.

### D. 조기 종결 대응 — "분리를 막는다"가 아니라 "분리돼도 의미/뉘앙스가 안 깨지게" (실사용
관찰, 다음 평가 라운드 전에 우선 처리 권장)
현재 CER/chrF++로는 안 잡히는 문제지만 실사용 체감 품질에 직접적. 두 가지 하위 케이스로
나눠서 접근한다.

**D-1. 단어/음절 중간에 물리적으로 잘린 경우** (예: "자아아암시.... 만요!"가 "자아아암" /
"시....만요"로 쪼개짐) — STT가 애초에 온전한 단어를 못 받았으므로 문맥을 아무리 잘 넘겨도
못 살린다. 분리 자체를 줄이는 수밖에 없음:
1. `_finalize_utterance` 발동을 즉시 하지 말고, 침묵 임계값을 넘긴 뒤 짧은 유예(grace)
   구간(예: 200~300ms)을 한 번 더 두고 그 사이 발화가 재개되면 같은 발화로 합침(디바운스).
   `_UtteranceState`에 "finalize 대기 중" 상태만 추가하면 됨 — 싸다.
2. (설계상 원래 계획된 것) `CLAUDE.md`가 요구하는 구두점/문맥 보정 단계를 실제로 구현 — STT
   partial 텍스트가 일본어 문장 종결 형태(だ/です/ます/か 등)로 끝나는지, 조사/어간(て/で/し
   등 후속을 요구하는 형태)으로 끝나는지를 보고 종결 여부를 보정. `VAD_SILENCE_MS`와 이
   보정 로직은 별도 튜너블로 유지(하나의 하드코딩 휴리스틱으로 합치지 말 것).

**D-2. 문법적으로는 멀쩡한 두 조각으로 잘렸는데 번역 어투/뉘앙스가 끊기는 경우** — 더 흔하고
고칠 여지도 더 큼. 지금 `translation/llama_server_engine.py`는 `context`로 직전 문장의
**일본어 원문만** 넘기고, `_FINAL_SYSTEM_PROMPT`가 "참고만 하고 절대 같이 번역하지 마라"고
못박아 놔서 조각 2가 독립된 새 문장처럼 번역되도록 강제돼 있음:
1. (싼 것) `context`에 직전 **한국어 번역문**도 같이 넘겨서 "이어지는 어투/존댓말 톤을
   유지해 자연스럽게 이어지게 번역하라"고 프롬프트 지침을 바꾼다 — `AudioSession`에
   `_last_final_translation_ko` 하나만 더 들고 다니면 됨.
2. 프롬프트를 "[PREVIOUS]가 문법적으로 안 끝난 것 같으면 자연스럽게 잇는 번역을 하라"로
   수정 (지금의 "따로 번역해라" 지침을 완화).
3. (더 크게 가면) 직전 문장이 미완결로 판단되면 두 조각을 합쳐 통째로 재번역하고, 화면에
   이미 표시된 직전 캡션을 새 번역으로 **교체**하는 "정정(correction)" 이벤트를 추가. UI가
   아직 없으니(로드맵 4단계) 지금 이벤트 프로토콜에 반영해두면 나중에 UI 쪽에서 다시
   설계할 필요가 없음. 1→2로 부족할 때 시도.

### E. 장기 맥락 메모리 (D-2를 넘어선 확장 — 사용자 제안)
D-2는 "직전 문장 1개"만 문맥으로 쓴다. 스트림이 길어질수록(예: 같은 화제/인물/사건이 몇
분에 걸쳐 이어짐) 직전 1문장만으로는 대명사·생략된 주어·화제 전환 같은 걸 못 잡는다.
계층적 메모리로 확장 제안:

- **단기 메모리**: 최근 완결된 문장(원문+번역) 최대 N개를 그대로 FIFO로 유지. N개 초과 시
  가장 오래된 것부터 버림.
- **장기 메모리(요약)**: 시동 후 문장이 10개 이상 쌓이면 최초 요약을 생성. 이후 J개 문장이
  새로 쌓일 때마다, 기존 요약 + 새로 쌓인 J개 문장을 합쳐 재요약한다 — 시간순 관계·인과
  관계·중요도를 따져서 정리하고, 오래됐거나 중요도가 낮아진 내용은 이 때 버릴 수 있다.
  요약 결과는 고정된 토큰 예산을 넘지 않도록 제한.
- 번역 호출 시 `context`로 "장기 요약 + 단기 최근 N개"를 함께 넘겨서 조각 번역이 전체
  화제/인물 관계와 어긋나지 않게 한다.

**구현 순서 제안 (싼 것부터)**:
1. 요약 없이 **단기 메모리(최근 N문장 그대로 이어붙이기)만 먼저** 넣어보고 D-2 문제가
   얼마나 개선되는지 확인 — 코드 몇 줄, 별도 LLM 호출 없음.
2. 그걸로 부족하면(스트림이 길어서 화제가 계속 바뀌는 경우 등) 장기 요약 단계를 추가.
   요약 생성은 현재 발화의 번역 응답 시간에 끼워 넣지 말고 **비동기로 백그라운드에서 갱신**
   — PRD의 1~2초 지연 목표를 깨지 않기 위함. 이번 요약이 다음 문장부터 반영되면 충분.
3. 요약을 만드는 데 쓰는 모델/프롬프트도 번역과 같은 llama-server를 재사용할지, 더 가벼운
   모델을 따로 둘지는 벤치마크 필요(패턴 C 벤치마크와 같이 진행하면 효율적).

### 부수 — 평가 방법론 보완
- `hard` 그룹 태깅 기준(현재: 필러/반복/은어 필드 존재 여부)이 실제 난이도와 역상관을
  보였다 — 표본을 늘리거나 태깅 기준을 다시 정의해야 다음 라운드 결과를 신뢰할 수 있음.
- 고유명사 CER(§2.2)이 이번 데이터셋에서 측정 불가(`sl_new_word` 필드가 거의 비어 있음) —
  글로서리 검증에 필요하니 다음 데이터셋 준비 시 고유명사 세그먼트를 직접 태깅해둘 것.
