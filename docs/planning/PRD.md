# PRD — live-translator

## 1. 한 줄 요약

유튜브 라이브 등 브라우저 탭에서 재생 중인 **일본어 음성**을 실시간으로 캡처해, STT(음성인식) →
번역을 거쳐 **자연스러운 한국어 자막**으로 보여주는 개인용 크롬 확장 프로그램.

## 2. 배경 / 문제 정의

- 사용자는 일본어 유튜브 라이브 방송을 자주 시청하지만 일본어를 실시간으로 알아듣지 못한다.
- 방송 종료 후 다시보기 자막이나 커뮤니티 번역을 기다리는 것은 "라이브"의 의미를 없앤다.
- 기존 브라우저 자동 자막(Chrome 라이브 캡션 등)은 번역 품질이 낮고 자연스러운 한국어로
  다듬어주지 않는다.

## 3. 목표 (Goals)

- 탭에서 나오는 일본어 음성을 끊김 없이 캡처한다.
- 발화 후 **1~2초 이내**로 한국어 번역 결과가 화면에 나타난다 (체감 실시간).
- 번역 결과가 직역투가 아니라 자연스러운 한국어 문장이어야 한다.
- 완전히 로컬에서 동작한다 (클라우드 API 비용/의존성 없음, 개인 사용 목적).

## 4. 목표가 아닌 것 (Non-goals, 최소한 v1에서는)

- 다국어 지원(우선 일본어→한국어만).
- 여러 사용자 동시 서비스, 배포/공개, 계정/과금 시스템.
- 완벽한 축자 번역/전사 정확도 — "실시간으로 대충 알아들을 수 있는 수준"이 우선.
- 마이크 음성 녹음 방식(스피커 소리 재캡처)은 v1 범위 밖.

## 5. 사용자 & 사용 시나리오

- **사용자**: 본인(1인) 전용 도구.
- **시나리오**: 일본어 유튜브 라이브 탭을 열어둔 채 확장 프로그램을 켜면, 화면에 실시간 한국어
  자막이 뜨거나(오버레이), 별도 패널에 스트리밍 텍스트로 쌓인다. 두 표시 방식 모두 지원한다.

## 6. 시스템 아키텍처 개요

```
[YouTube 등 브라우저 탭 오디오]
        │  chrome.tabCapture
        ▼
[크롬 확장 프로그램 (extension/)]
        │  오디오 청크 스트리밍 (WebSocket)
        ▼
[로컬 백엔드 (backend/, FastAPI + WebSocket)]
        │
        ├─ STT 단계 (일본어 음성 → 일본어 텍스트)
        │
        └─ 번역 단계 (일본어 텍스트 → 자연스러운 한국어)
        │
        ▼  WebSocket으로 결과 스트리밍
[크롬 확장 프로그램: 오버레이 자막 / 사이드 패널 표시]
```

- **오디오 캡처**: 크롬 확장 프로그램의 `chrome.tabCapture`. 별도 화면공유 승인 없이 탭을
  백그라운드에 둔 채로도 계속 캡처 가능 — `getDisplayMedia` 방식보다 반복 승인이 없어 선호됨.
- **백엔드**: NVIDIA GPU(CUDA)를 활용하는 로컬 Python(FastAPI + WebSocket) 서버. 확장 프로그램과
  1:1로 로컬에서 통신하며 외부 네트워크로 나가지 않는다.
- **출력 UI**: (a) 재생 중인 영상 위에 겹쳐 뜨는 오버레이 자막, (b) 확장 프로그램의 별도
  패널/사이드바에 스트리밍되는 텍스트 로그 — 두 방식 모두 지원.

## 7. 스트리밍 / 문장 완성 전략

오디오는 **0.3초 단위 청크**로 잘라 백엔드에 연속 전송한다 (지연시간보다 반응성 우선; 추후
설정값으로 0.3~0.5초 사이 조절 가능하게 만든다). 화면에는 항상 두 가지 상태의 텍스트가 함께
존재할 수 있다:

1. **미완성(진행 중) 문장** — 현재 발화 중인 문장. 단어 단위로만 받아적히며(스트리밍 STT의
   부분 가설), 번역도 문맥을 살려 자연스럽게 시도하되 문맥 판단이 어려우면 **단어 그대로의 간단
   직역**까지만 제공한다. 완벽함보다 "일단 뭔가 뜬다"가 우선.
2. **완성된 문장** — 문장이 끝났다고 판단되면, 전사 결과를 자연스럽게 다듬고 번역도 문맥을 반영한
   자연스러운 한국어 문장으로 **교체**한다.

**문장 완성 판단**은 두 신호를 조합한다:
- 1차 신호(침묵 기반): 일정 시간 이상 음성이 끊기면 문장 종료 후보로 간주.
- 보정(문맥 기반): 구두점/문맥상 문장이 실제로 끝났는지 STT·번역 단계에서 다시 판단해 최종
  확정한다. (상대가 말을 자주 쉬면 침묵만으로는 문장이 부자연스럽게 잘릴 수 있으므로 필요)

**UI 표시**는 미완성/완성 상태를 시각적으로 구별한다 — 미완성 문장은 흐리게/어둡게, 완성된
문장은 밝고 선명하게 표시해 사용자가 "아직 다듬어지는 중"인지 "확정된 번역"인지 한눈에 알 수
있게 한다. (오버레이 자막, 사이드 패널 모두 동일한 구별 규칙 적용)

## 8. STT / 번역 모델 정책

**속도와 품질을 직접 비교해본 뒤 가장 적합한 조합을 선택**하는 것을 원칙으로 한다.

**현황 (2026-08-18 벤치마크 완료)**: STT는 faster-whisper `medium`(CUDA, int8_float16),
번역은 llama.cpp server로 서빙하는 **gemma-3-12b-it Q4_K_M** 채택
(`docs/eval/MODEL_BENCHMARK_PLAN.md`, `docs/eval/EVAL_REPORT_gemma-3-12b-it_2026-08-18.md`).
벤치 1위였던 Qwen3-14B는 한글 강제 grammar와의 비호환으로 보류. 아래의 후보군 서술은
선정 당시 기준이며, 교체 가능 설계 원칙은 계속 유효하다.

- STT: whisper.cpp / faster-whisper 등 로컬 실행 가능한 후보군을 비교. 후보군에 whisper 계열보다
  더 상위/최신 성능의 모델이 있다면 그쪽도 함께 검토 대상에 포함한다.
- 번역: Ollama 등 로컬 LLM 서빙 후보군을 비교. Ollama보다 더 빠르게 출력 가능한 로컬 서빙
  방식(예: llama.cpp server, vLLM 등)이 있다면 함께 검토한다.
- **구현 시 설계 원칙**: STT 엔진과 번역 엔진은 백엔드 내부에서 교체 가능한 컴포넌트로 분리
  구현한다 (특정 모델/라이브러리에 하드코딩하지 않음) — 벤치마크 후 모델을 바꿔 끼울 수 있도록.

## 9. MVP 개발 순서 (파이프라인을 단계별로 나누어 순차 검증)

각 단계는 이전 단계가 눈으로 확인 가능한 수준까지 동작해야 다음 단계로 넘어간다.

1. **캡처 + STT 검증**: 확장 프로그램이 탭 오디오를 0.3초 청크로 캡처해 백엔드로 전송하고,
   백엔드가 일본어 텍스트 전사 결과(미완성/완성 구분 포함)를 콘솔/간단한 화면에 출력한다.
   (번역 없음, UI 없음)
2. **번역 추가**: 미완성 문장은 간단 직역, 완성된 문장은 자연스러운 번역으로 콘솔/간단한
   화면에 출력한다.
3. **오버레이 UI 추가**: 번역 결과를 실제 유튜브 영상 위 오버레이 자막 + 사이드 패널에
   미완성/완성 시각적 구별과 함께 스트리밍으로 표시한다.

## 10. 성공 기준 (v1)

- 일본어 유튜브 라이브를 켠 상태에서, 발화 후 1~2초 내 한국어 자막이 화면에 나타난다.
- 문장이 진행되는 동안에도 단어 단위로 뭔가 계속 뜨고(미완성), 문장이 끝나면 자연스러운
  번역으로 매끄럽게 교체된다.
- 자막이 기계적 직역이 아니라 자연스러운 한국어 문장으로 읽힌다 (완성된 문장 기준).
- 별도 클라우드 API 키/네트워크 요청 없이 완전히 로컬에서 동작한다.

- ~~STT/번역 모델 최종 선정~~ — **완료** (§8 현황 참고).
- 침묵 기반 문장-종료 판단의 구체적 임계값(몇 ms 무음이면 종료 후보로 볼지) — 현재값은

- 긴 침묵/음악 구간 등 번역이 불필요한 구간을 건너뛰는 로직 필요 여부. (현재는 VAD/no_speech
  필터의 부수효과로 노래 구간이 대부분 걸러지는 상태 — 노래 가사까지 전사/번역할지, 지금처럼
  건너뛸지는 **추후 계획**으로 남겨두고 당장은 손대지 않는다.)
- **역방향(한국어→일본어) 채팅 메시지 번역** (2026-08-19 제안, UI 단계에서 착수 — 지금은 손대지
  않음): 사용자가 스트리머에게 보낼 한국어 메시지를 입력하면 자연스러운 일본어 텍스트로
  번역해주는 기능. 지금의 청취용(일본어 음성→한국어) 파이프라인과는 **완전히 독립적으로
  비동기 동작**해야 함 — 구조적으로는 이미 가능한 상태:
  - `AudioSession`(청취 파이프라인)은 웹소켓 연결/오디오 스트림에 종속된 상태라, 새 기능은
    별도 요청 경로(새 REST 엔드포인트 또는 별도 웹소켓)로 텍스트 하나 받아 번역해 돌려주는
    식으로 얹으면 됨 — 오디오/STT와 상태를 공유할 필요 없음.
  - llama-server가 이미 멀티 슬롯(`n_slots = 4`)으로 동시 요청을 처리하고, 청취 쪽 최종
    번역도 `AudioSession`의 백그라운드 워커 큐(`_finalize_queue`)로 빠져 있어서(오디오
    수신을 막지 않음), 양방향이 서로 블로킹 없이 동시에 돌아갈 수 있는 기반이 이미 갖춰짐.
  - 방향이 반대라 프롬프트는 새로 설계해야 함(한국어 존댓말/반말 판단 → 일본어 대응,
    `llama_server_engine.py`의 기존 KO 전용 grammar/노트들은 이 방향엔 안 맞음).
